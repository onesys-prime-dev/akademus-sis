1Executive Summary

1.1 Architectural overview

The Student Information System's academic-operations core is built from four independently-developed, independently-validated subsystems, each solving a distinct combinatorial problem in university scheduling, plus a master orchestrator that runs and audits all four as a single suite:

#SubsystemProblem Solved
1scheduler_qaAssign every course session a (day, time, room) with no overlaps
2section_balancing_qaSplit oversized course enrollments into balanced sections
3integrated_pipeline_qaCompose (1) and (2) into one enrollment-to-timetable pipeline
4student_audit_qaCatch and resolve conflicts in an individual student's combined schedule

Each was built, tested, and documented as a standalone unit before being composed — the architecture is deliberately a suite of narrow, provably correct tools rather than one monolithic scheduler, the same way a compiler is built as separate lexer/parser/codegen stages: each stage is independently testable and composable without re-deriving correctness at the seams.

1.2 Mathematical classification

Both of the suite's core combinatorial problems belong to well-known NP-hard / NP-complete complexity classes:

  • University course timetabling generalizes graph coloring and multi-dimensional bin packing — NP-complete in general, with no known polynomial-time algorithm for the general case.
  • Student section load balancing is an instance of Multiway Number Partitioning (Balanced Bin Packing).

Neither subsystem "solves NP-hardness away." Each exploits the specific structure of its problem instance — heuristic variable ordering for the CSP, closed-form arithmetic partitioning for the bin-packing problem — to reach a provably optimal or near-optimal solution in practical, polynomial time.

1.3 Microservice decoupling strategy

The suite's defining architectural decision is decoupling sectioning from scheduling: a scheduler reasoning about raw enrollment directly must explode its variable count to one-per-student, or fail outright once enrollment exceeds a room's capacity. Resolving "how many sections, how many students in each" before scheduling begins — as pure O(1) arithmetic, not search — keeps the CSP's branching factor bound to the number of sections, never the number of students.

2Subsystem 1: Timetable Scheduling Engine scheduler_qa

2.1 Formulation

Modeled as a classic Constraint Satisfaction Problem: one variable per required weekly session (67 variables across 40 courses), whose domain is every (timeslot, room) pair not yet ruled out by a hard constraint, recomputed fresh at each step (forward checking).

2.2 Algorithmic strategy: MRV, zero-backtrack resolution

At every step, the solver assigns the still-unassigned variable with the smallest live domain first (Minimum Remaining Values) — forcing the tightest constraints (two professors each carrying 5 courses against 13–14 blocked timeslots out of 45) to resolve while the most options still exist.

ResultAll 67 sessions placed in exactly 67 search steps, zero backtracking required — every first decision remained valid for the entire search.

3Subsystem 2: Section Load Balancer section_balancing_qa

3.1 Formulation

An instance of Balanced Bin Packing / Multiway Number Partitioning: divide N enrolled students into the fewest groups fitting under room capacity C, as close in size as possible.

3.2 Algorithmic strategy: O(1) partitioning

k = ceil(N / C)             # minimum sections required
L = ceil(N / k)             # size of the largest section in a perfect split
base, remainder = divmod(N, k)
sizes = [base+1]*remainder + [base]*(k-remainder)
CourseNCkSizes
ITS10114132[7, 7]
CS10182303[28, 27, 27]
ENG20043203[15, 14, 14]
BUS40018251[18]

3.3 Achievable-optimum quality metric

The naive formula Σ(ActualSize − L_target)² is non-zero even for the best possible split whenever N doesn't divide evenly by k — scoring the provably optimal [28,27,27] split as penalty 2, not 0. The fix: compare actual penalty against the achievable minimum, failing only when strictly worse:

FAIL only if:  Penalty_actual  >  Penalty_min_achievable
Proven to still catch real imbalance A self-test deliberately rebalancing ITS101 into [13,1] scored penalty 72 vs. achievable-minimum 0 — correctly flagged, with the exact fix recommended: "Move 6 student(s) from ITS101-SEC1 to ITS101-SEC2." Result: 4/4 test cases hit their exact divmod-optimal partition.

4Subsystem 3: Integrated 2-Stage Pipeline integrated_pipeline_qa

4.1 Pipeline flow

 raw enrollment demand         Stage 1 output                final timetable
┌────────────────⓬  Stage 1  ┌──────────────⓬ Stage 2  ┌──────────────⓬
│ courses, N          │───────◀│ discrete, sized     │───────◀│ sections + sessions │
│ students, rooms,   │ Section │ SECTION objects     │  CSP    │ + rooms + days/times│
│ professors         │ Balancer│ (coreq-paired)       │Scheduler│(validated)          │
└───────────────┘         └──────────────┘         └──────────────┘

Stage 1 converts raw enrollment into k right-sized section objects and resolves course-level corequisites into section-level pairings (ITS101's 1st section paired with ITS101L's 1st section specifically). Stage 2 then schedules those sections as any other CSP instance.

4.2 State-space pruning

Without Stage 1, Stage 2 would need one variable per student (combinatorially larger) or one variable per course (unsolvable once N exceeds any room's capacity). Stage 1's O(1) partitioning resolves this before search begins, so Stage 2's variable count is bounded by sections × sessions/week, never by student count — the test dataset's 103 students produced only 12 CSP variables across 7 sections, with students entirely invisible to Stage 2's search.

5Subsystem 4: Student Schedule Conflict Auto-Resolver student_audit_qa

5.1 Problem domain

A room scheduler and a section-balancing engine can both be individually perfect and a student can still end up with an impossible personal schedule — invisible to both other subsystems since it is purely a property of one student's combination of registrations.

5.2 Resolution engine

Pairwise overlap detection flattens each student's registered sections into a personal schedule and checks every pair for a shared (day, start_time). Capacity-aware auto-resolution then searches for an alternate section satisfying both:

  1. Time Non-Interference — zero overlap with the student's remaining schedule.
  2. Capacity Limit Enforcement — current_enrollment(alt) + 1 ≤ max_capacity(alt).

5.3 Atomic state updates & fail-safe logic

A successful reassignment updates the student's registration and live section headcounts together, atomically. If no alternate satisfies both constraints, nothing is partially mutated:

[FAIL - CAPACITY EXHAUSTED] No alternate section ... satisfies both
    time non-interference and capacity headroom.
[RECOMMENDED FIX] Open additional section for course X or Y, or
    increase room capacity for an existing alternate section.

6System Orchestration & Diagnostic QA Suite main.py

6.1 Architecture

A root-level master CLI orchestrator runs all four subsystems as isolated subprocesses — never importing their code directly, with cwd scoped to each subsystem's own directory. This guarantees zero cross-module file contention.

Cross-platform resilience: Windows consoles default to legacy CP1252, which cannot render Unicode box-drawing. The orchestrator attempts a UTF-8 reconfigure at startup and falls back to ASCII box-drawing if unavailable — discovered and fixed during this suite's own verification.

FlagBehavior
(none)Run all 4 modules sequentially
--module <name>Run exactly one module
--verboseStream full stdout/stderr live
--reportWrite aggregated JSON to master_audit_report.json
