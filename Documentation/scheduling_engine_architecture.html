1Executive Summary

University course timetabling — assigning every course session a (day, time, room) slot such that no professor, room, or corequisite relationship is double-booked — belongs to a well-known class of NP-complete combinatorial problems. It generalizes graph coloring and multi-dimensional bin packing: as courses, rooms, and professor-availability restrictions grow, the candidate-assignment space grows combinatorially, and no known algorithm solves the general case in polynomial time. A production timetabling engine therefore cannot rely on brute-force enumeration — it must prune the search space intelligently enough that a solution, if one exists, is found in a tractable number of steps.

This engine was tested against a deliberately adversarial synthetic dataset: 40 courses (67 weekly sessions), 10 rooms across 3 buildings, 15 professors, and 45 weekly timeslots, with three engineered bottlenecks — two professors carrying 5 courses each against 13–14 blocked timeslots, tight Lab-capacity-vs-enrollment fits, and only two lecture halls large enough for the four biggest classes.

Result The CSP solver, using a Minimum-Remaining-Values (MRV) variable-ordering heuristic, placed all 67 sessions in exactly 67 search steps with zero backtracking — every first decision remained valid for the entire search. The schedule passed all six hard constraints with zero violations and scored 28.0/100 on soft quality constraints, a figure this report shows is the structural ceiling imposed by the campus's physical room layout, not an algorithmic shortfall.

2Algorithmic Approach

2.1 Problem formulation as a CSP

The engine models timetabling as a classic Constraint Satisfaction Problem:

  • Variables — one per required session. A course meeting N times/week contributes N independent variables. 40 courses produced 67 variables.
  • Domain — for each variable, every (timeslot, room) pair that does not yet violate a hard constraint, recomputed fresh at each step against the current partial assignment (forward checking).
  • Constraints — the six hard rules in Section 3, plus the implicit CSP rule that no two variables may resolve into conflict.

2.2 Variable ordering: Minimum Remaining Values (MRV)

At every step, the solver scans all unassigned variables, computes each one's live domain size, and commits to the variable with the smallest domain first — rather than assigning in an arbitrary course-list order.

This matters because the dataset's bottlenecks are unevenly distributed. Professors P03 and P11 are each unavailable for 13–14 of 45 weekly timeslots (vs. 3–6 for everyone else) while carrying 5 courses apiece. Left until the end of a naive search, their sessions would frequently find all remaining options already consumed by looser-constrained courses, forcing expensive backtracking or outright failure. MRV instead resolves the tightest constraints while the most options still exist — the single biggest lever in CSP performance for problems shaped like this one.

2.3 Value ordering: soft-score-aware heuristic

Where MRV decides which variable to assign next, a secondary heuristic ranks which candidate within that variable's domain to try first, scored on:

  • Room-fit waste — (capacity − enrollment) / capacity, smaller is better.
  • Corequisite proximity — same-day time gap to any already-placed partner session, smaller is better.

Candidates are tried best-scored-first, so the search finds a good schedule on the same pass it finds a legal one — no separate optimization phase is required.

2.4 Backtracking as a safety net, not the primary mechanism

Classic backtracking is implemented (400,000-step ceiling, up to 30 randomized-restart attempts) but was never invoked in this run. The MRV ordering alone reached a complete, valid assignment of all 67 sessions in 67 steps — one step per variable, no retries. This is the strongest possible signal that the heuristic ordering was well matched to this problem instance's structure.

3Constraint Resolution (Hard Limits)

Every hard constraint is enforced structurally: a candidate is never added to a variable's domain if it would violate a rule, rather than being checked after the fact. Any committed assignment is legal by construction.

#ConstraintEnforcement mechanism
1Room overlapA booked (room, timeslot) pair is removed from every other variable's domain instantly.
2Professor overlapA booked (professor, timeslot) pair blocks every other course taught by that professor at that slot.
3CapacityRooms are only candidates where capacity ≥ enrollment, pre-sorted smallest-fit-first.
4Room typeCandidate rooms are pre-filtered to the course's required type (Lecture / Seminar / Lab).
5Professor availabilityEach course's domain excludes its professor's unavailable timeslots up front.
6Corequisite overlapA course's domain excludes timeslots already claimed by any corequisite partner, checked symmetrically.
Independent verification A separate, independently-written validator (validate_schedule.py) re-derives every fact from dataset.json rather than trusting the solver's internal state, and confirmed zero violations across all six categories on the final schedule.

4Structural Optimization (Soft Score Analysis)

The validated schedule scored 28.0 / 100 on soft constraints. This section accounts for exactly where the 72 lost points went.

4.1 What was not penalized

  • Underfilled rooms — zero penalty. The room-fit heuristic consistently chose the smallest sufficient room for every course.
  • Corequisite time gaps — zero penalty. All 10 corequisite relationships achieved the minimum possible same-day gap between paired sessions.

4.2 What was penalized: corequisite building splits

All 72 lost points came from one category:

Why this is physical, not algorithmic: every Lecture+Lab corequisite pair pairs a Lecture-type session with a Lab-type session. Cross-referencing the room list by building:

BuildingRoom types present

Structural ceiling, not a bug No building on this campus contains both a Lecture-type room and a Lab-type room. Every possible placement of a Lecture+Lab corequisite pair is, by construction, split across buildings — there is no assignment anywhere in the solution space that avoids this for these 9 pairs. The achievable ceiling under this room layout is exactly 100 − (9 × 8.00) = 28.0, and the solver reached it precisely, losing zero further points to any avoidable soft penalty. Improving this score requires a facilities decision (co-locating a Lab with Lecture capacity), not a scheduling algorithm change.

5Frontend UI Integration

The validated schedule is rendered for human review in timetable.html, generated by exporter.py:

  • Grouped by room, not professor — 10 rooms vs. 15 professors fits a normal screen width without horizontal scrolling; "is this room free now" is the more common lookup.
  • Sticky header row — room ID, name, building, and capacity stay pinned while scrolling the Mon–Fri / 08:00–17:00 grid.
  • Department color coding — each cell is tinted and left-bordered by department color, with a legend, making cross-department room contention scannable at a glance.
  • Capacity metrics in-line — each room header shows capacity directly, enabling a sanity check without cross-referencing dataset.json.

Together with the companion master_schedule.csv (a flat, chronologically-sorted export), these form the two SIS-facing deliverables: one for human visual review, one for direct database ingestion.
