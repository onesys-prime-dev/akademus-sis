1Executive Architecture

This pipeline composes two previously-validated, independently-tested engines — Section Load Balancing and CSP Timetable Scheduling — into a single, ordered, two-stage system, structured deliberately like a microservice pipeline rather than one monolithic solver.

raw enrollment demand Stage 1 output final timetable ┌──────────────────⓬ Stage 1 ┌───────────────────⓬ Stage 2 ┌───────────────────⓬ │ pipeline_dataset │ ────────◀ │ discrete, sized │ ────────◀ │ integrated_schedule │ │ (courses, N │ Section │ SECTION objects │ CSP │ (sections + sessions│ │ students, rooms, │ Load │ (SEC1, SEC2, ... │ Timetable │ + rooms + days + │ │ professors) │ Balancer │ each pre-sized & │ Scheduler │ times, validated) │ └───────────────────┘ │ coreq-paired) │ └───────────────────┘ └───────────────────┘

Each stage has a single, narrow responsibility and a clean, serializable hand-off object between them — a list of section dictionaries, each fully self-describing. Stage 2 has zero knowledge of student enrollment counts or room capacity math — those questions were already answered by Stage 1. Section 3 shows this separation is what keeps Stage 2's search tractable.

2Data Flow Model

2.1 Input: raw course enrollment

pipeline_dataset.json describes courses purely in real-world terms: enrollment count, room capacity, required room type, professor, and corequisite relationships. Nothing is pre-partitioned or schedule-aware.

2.2 Stage 1: enrollment → k balanced section entities

k = ceil(N / C)
base, remainder = divmod(N, k)
sizes = [base+1]*remainder + [base]*(k-remainder)

This yields concrete objects like ITS101-SEC1 (7 students) and ITS101-SEC2 (7 students) — no longer "a course," but k independent, schedulable units.

Corequisite resolution happens here too. The dataset declares corequisites at the course level, but Stage 2 needs to know which sections must not overlap. Stage 1 pairs each course's generated sections positionally (1st with 1st, 2nd with 2nd) and stamps the result as corequisite_section_id — Stage 2 never reasons about course-level relationships at all.

2.3 Stage 2: sections → mapped room/time slots

Stage 2 ingests the Stage 1 section list as its entire input. Each section contributes one CSP variable per required weekly session, and the same MRV-ordered backtracking search validated in the standalone scheduling engine assigns each one a (day, time, room) triple.

2.4 Output: the fully resolved, nested schedule

integrated_schedule.json nests each section's Stage 1 result (roster) with its Stage 2 result (sessions), so the artifact documents the full pipeline's work on that unit in one record.

3Algorithmic Convergence

3.1 Why decoupling prevents state-space explosion

A CSP search's cost is driven by its branching factor per variable and its variable count. Without Stage 1, Stage 2 would have to either reason about one variable per student (combinatorially larger) or treat a whole course as one variable — which is simply unsolvable once N exceeds any single room's capacity.

Stage 1's O(1) partitioning resolves this before search begins — pure arithmetic, not search — producing exactly k well-formed variables per course, the true minimum needed:

  • Stage 2's variable count is bounded by sections × sessions/week, not by student count. This dataset's 103 enrolled students produced only 12 CSP variables across 7 sections.
  • Students are invisible to Stage 2's search — they are payload Stage 1 already finalized.

3.2 Empirical result: zero backtracking at the seam

=== STAGE 1: Section Load Balancer ===
  ITS101-SEC1: 7 students ... coreq -> ITS101L-SEC1
  ITS101-SEC2: 7 students ... coreq -> ITS101L-SEC2
  ITS101L-SEC1: 7 students ... coreq -> ITS101-SEC1
  ITS101L-SEC2: 7 students ... coreq -> ITS101-SEC2
  CS101-SEC1: 28 students ... coreq -> None
  CS101-SEC2: 27 students ... coreq -> None
  MATH201-SEC1: 20 students ... coreq -> None

=== STAGE 2: CSP Timetable Scheduler ===
  Stage 2 attempt 1/30 (backtracking search)...
  Solved in 12 search step(s), 0 of which backtracked past the first try.

12 variables, 12 steps, zero backtracking — the MRV heuristic found a fully consistent assignment on the first attempt, the observable proof of the convergence argument above.
